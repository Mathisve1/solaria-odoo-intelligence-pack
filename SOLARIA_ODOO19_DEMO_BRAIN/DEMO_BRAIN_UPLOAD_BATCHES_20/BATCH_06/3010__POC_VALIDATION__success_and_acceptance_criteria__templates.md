# Success Criteria, Acceptance Criteria and the Proof-Point Register

Category: POC_VALIDATION.

## Success-criteria template (per claim under proof)
```
Claim (verbatim from validation register): ...
Metric: what we count/measure
Method: how it is measured, by whom, on which data
Threshold: the signed pass value (agreed BEFORE data is seen)
Sample: volume/period of client data used
Date: when measured
Owner (client) / Owner (Deloitte): named people
```
Examples of well-formed thresholds: 'touchless rate >= X percent on one month of real vendor bills, X agreed at kickoff'; 'the three named pricing cases compute correctly on 20 real quotes'; 'pick flow completes in <= N scans for the standard order profile'.

## Acceptance criteria rules
- Written before the POC starts; signed by the client evaluation owner.
- Pass/fail per criterion; no averaged verdicts across unrelated claims.
- Partial passes produce named residual risks, not fuzzy 'mostly works' conclusions.
- AI criteria always two-part: capability ran (existence) AND quality threshold met on client data.

## Proof-point register (the POC's running truth)
| Claim | Criterion | Status (open/pass/fail) | Evidence link | Decided on | Notes |
Updated at every POC checkpoint; presented as-is at evaluation (unedited history builds trust).

## Evaluation session pattern
Criteria table first, one by one, evidence shown; then residual risks; then the consequence clause executed (next step or stop). No new scope negotiated in the evaluation room.
