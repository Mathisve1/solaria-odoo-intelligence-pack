# Standard Before Custom: Demo Logic

| Attribute | Value |
|---|---|
| Foundation file | 0010 of 20 |
| Basis | The Deloitte solution ladder from the Odoo 19.0 Intelligence Pack, adapted for demo situations |

## 1. The ladder (classify every demo recommendation)
1. **Standard Odoo:** shipped behaviour of installed modules, as designed.
2. **Configuration:** settings, master data, stages, routes, pricelists, SLA policies, approval settings.
3. **Studio:** Enterprise no-code shape changes (fields, views, approval rules on actions), governed.
4. **Automation:** automation rules and server actions (Community capability; AI steps are Enterprise).
5. **Custom module:** developed extension; owned, tested, upgrade-taxed.
6. **External integration:** the capability lives in another system; Odoo exchanges data.
7. **Validation required:** we believe but have not verified; explicitly parked for a live check.

Every element of a demo plan carries its level. The classification appears in the internal plan always, and in the room whenever the client could otherwise mistake the level.

## 2. The demo-specific rules
- **Never demonstrate a custom concept as if it were standard Odoo.** If a mock-up, Studio build or prototype appears in a demo, it is introduced as exactly that ("what we would build for you"), before it is shown, not after.
- **Standard first on screen:** show the native flow before any tailored variant, so the client learns what the product gives them versus what is added for them. This ordering also protects the fit-gap conversation later.
- **Configuration is a wow moment in itself:** live-changing a stage, an approval threshold or a pricelist rule ("this is a setting, not a project") is one of the most persuasive things a demo can do. Use it deliberately.
- **Studio in demos:** only for Enterprise conversations; always with the governance sentence (registry, staging, export); never to fake product behaviour that would really be custom logic.
- **Automation in demos:** show a rule being created live when the client's challenge is process discipline; label it Community-available.
- **Custom moments:** only when the fit-gap genuinely points there, and always with implementation realism attached (owner, effort class direction, upgrade note).
- **Integration moments:** name the boundary honestly ("Odoo stops here; your carrier system does this part"); demo the Odoo side; never simulate the other system without saying so.

## 3. Level discipline in client language
The room hears plain language, but the language must not launder the level: "out of the box" only for level 1; "a setting we switch on" for level 2; "tailored without code, governed" for level 3/4; "built for you" for level 5; "connected to your existing system" for level 6; "we will confirm this on a live system" for level 7.

## 4. When the user pushes to skip the ladder
If a Deloitte user asks to present a custom idea as standard, or to promise a capability without classification, the brain declines, states this rule, and offers the honest alternative phrasing plus the validation step that could upgrade the claim. This mirrors the non-negotiables in file 0002 and the claim labels in file 0018.
